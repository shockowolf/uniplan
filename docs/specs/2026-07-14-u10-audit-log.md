# U10 — Transactional append-only audit log

## Goal

Add a production-grade, tenant-scoped audit trail for authentication and every U1–U9 critical mutation. Audit writes must be append-only, bounded, PII-minimized, derived from trusted server/session context, and atomic with the business mutation whenever both are database writes.

## Additive model and migration

Add `AuditEvent` with:

- immutable high-entropy ID;
- `companyId` relation and optional `actorUserId` tenant-composite relation;
- bounded `action`, `resourceType`, optional opaque `resourceId`;
- bounded `outcome` enum (`succeeded`, `denied`, `failed`);
- bounded request/correlation ID and optional idempotency key hash, never raw key;
- bounded JSON metadata allow-list with no email, company code, names, password, token, cookie, raw request body, birth/contact/customer text, inventory note, or exception stack;
- server timestamp;
- useful tenant/time/action/resource indexes.

Add PostgreSQL triggers that reject UPDATE and DELETE. Only INSERT is allowed. Do not use a session GUC as the only authorization boundary.

Migration is additive and must preserve public schema row counts/fingerprints for all existing columns.

## Trusted audit service

Implement a central server-only audit service that:

- validates bounded action/resource/outcome/metadata;
- rejects PII-like keys and oversized/deep values using an allow-list;
- hashes idempotency/correlation material with a production-required HMAC secret if it must be persisted;
- accepts an existing Prisma transaction so business row(s) and audit row commit or roll back together;
- exposes no client-controlled company/actor override;
- maps errors to stable domain errors without leaking raw Prisma details.

## Required coverage

Audit at least:

### Authentication

- login succeeded, denied and rate-limited;
- logout/revocation succeeded or failed;
- invited password reset and session revocation;
- session cleanup summary as a system actor.

Failed unauthenticated login events must not store raw company code/email. Use a one-way production-secret HMAC subject bucket and no actor relation.

### Business mutations

- item/category create/update/activate/deactivate;
- warehouse create/update/activate/deactivate;
- BOM create/revision/component/activation/deactivation;
- inventory posting/reversal/production with transaction resource and actor;
- navigation create/update/reparent/activate/deactivate.

The trusted actor must come from the authenticated session or the existing server-derived inventory actor. If a domain function currently lacks actor context, add an explicit trusted actor parameter at the API/service boundary; never read it from request JSON.

## Atomicity and failure behavior

- For each successful business mutation, its audit insert occurs inside the same U9 company mutation transaction.
- Injected audit failure rolls back the business mutation.
- Injected business failure writes no misleading success event.
- Denied API/auth attempts may be recorded in a separate bounded transaction because no business transaction exists.
- Duplicate idempotent business replay must not create duplicate success audit rows; use a unique semantic dedupe key where applicable.
- Retried Serializable transactions must not duplicate audit rows.

## Audit read API

Add a tenant-scoped read-only API only if the existing permission model has or can add a dedicated `system.audit` read permission safely.

- real session required;
- no company/user spoofing;
- cursor pagination with bounded page size;
- bounded filters for time/action/resource/outcome;
- newest first;
- response allow-list; no internal hash, stack, or hidden metadata;
- `Cache-Control: private, no-store` and `Vary: Cookie`;
- tenant isolation and permission-denied tests.

Do not add a large admin UI in this task. A minimal existing system page readout is optional only if it requires a very small diff.

## Tests

- PostgreSQL append-only UPDATE/DELETE rejection;
- cross-tenant actor relation rejection;
- every critical mutation emits exactly one success audit row;
- true-parallel idempotent replay does not duplicate audit;
- Serializable retry does not duplicate audit;
- injected audit failure rolls back business state;
- injected business failure creates no success audit;
- failed login contains no raw identifier/password/token;
- metadata rejects PII-like keys, deep/large values and unsafe strings;
- audit read route session/RBAC/tenant/cursor/cache behavior;
- migration public pre/post fingerprint identical for existing tables/columns;
- no raw secrets or personal/business free text in persisted/logged audit data.

All destructive tests use a new explicit disposable schema guard. Never reset/truncate/seed the application public schema.

## Non-goals

- No backup/offsite storage, SIEM export, alerting, public admin UI redesign, billing, data export/import, deploy, or external log vendor.

## Verification

- focused audit/integration/concurrency tests;
- full tests, typecheck, production build;
- migration deploy/status/schema diff and public fingerprint compare;
- static coverage map proving all critical mutation entry points call the audit boundary;
- diff-check and secret scan;
- no commit/push/deploy by the implementation agent.
